# DeepSeek-Otter 桌面端设计方案

把 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（下称 dsh）打包成 Windows / macOS 桌面应用的产品与技术设计。README 面向人，介绍项目定位与方案结论；实现细节随代码演进放在各模块文档中。

## 项目定位

dsh 是 DeepSeek 官方的开源 agent harness，一切皆插件（基于 Cordis 框架），默认形态是 `npx @deepseek-ai/dsh web` 启动本地 Web UI（`http://127.0.0.1:3080`）。它要求用户先装 Node.js、会用命令行，普通用户无法直接使用。

DeepSeek-Otter（水獭）的目标：**让不懂命令行的用户也能一键安装、开箱即用地用上 dsh**——下载即用，无需 Node.js、无需终端，自动管理 dsh 后端与版本，并以桌面 App 的形态提供窗口、托盘、更新等原生体验。

一句话：**Otter 是 dsh 的桌面发行版（desktop distribution），对上游只做"打包与包装"，不 fork 功能。**

## 调研结论（选型的依据）

截至 2026-09 的三个关键事实：

1. **官方仓库已内置 Electron 桌面应用**（`apps/desktop`）。它的设计非常重：Electron 与 `@deepseek-ai/dsh` 绑定精确版本、内置离线 pnpm 种子、私有 `dsh-app://` 协议承载 Fetch 流量（不开任何监听端口）、staging/健康检查/回滚的激活事务。它解决的是"官方签名发行"问题，需要 macOS 公证、Windows EV 证书等生产发布环境，门槛高（相关文档：`docs/architecture.md` 的 "Desktop application" 一节、`apps/desktop/README.md`）。
2. `dsh web` 就是一个**完整的 Web UI**（会话、插件市场、设置、凭据都在里面），并且 dsh 提供多种启动 profile：`web`（Web 服务）、`headless`（一次性运行）、`sdk` / `sdk-minimal`（JSON-RPC SDK 服务）、`acp`（自动化协议服务）。这是桌面壳可以复用的核心资产。
3. **社区已有同类先例**：anywhere-labs/dsh-desktop（约 2.5 万 star），采用"薄 Electron 宿主 + 回环 HTTP/WS 加载官方 Web UI"路线，验证了这条路是通的且社区认可。

**推论：不要自研 Web UI，也不要 fork dsh**。官方 Web UI 就是产品本体，桌面壳只负责进程管理、窗口和原生集成。自研 UI 面对的是 developer preview 阶段"每周都在变的 API"（官方明示会有破坏性变更），维护成本不可控；而 Web UI 由上游随版本一起发布，天然同步。

## 候选方案对比

| 方案                     | 思路                                | 优点                                             | 缺点                                                       | 结论                       |
| ------------------------ | ----------------------------------- | ------------------------------------------------ | ---------------------------------------------------------- | -------------------------- |
| A. 薄壳 Electron + Web UI | Electron 起 `dsh web`，窗口加载回环地址 | 实现最快；官方 UI 原汁原味、随上游升级零成本；社区已验证 | Electron 体积大；UI 完全依赖上游，无自研差异化              | **推荐**                   |
| A'. 社区 dsh-desktop     | 直接用现成的 anywhere-labs 产品     | 零开发                                           | 不是自己的产品，无法定制                                   | 不采用，仅作参考           |
| B. Tauri + 回环加载      | Rust 壳起 dsh 子进程，WebView 加载  | 壳本体体积小（~10 MB 级）                        | dsh 是 Node 生态，仍需打包 Node 运行时，体积优势蒸发；Windows WebView2 版本一致性风险；Rust 工具链对贡献者不友好 | 不采用                     |
| C. 自研 UI + SDK profile | `dsh --profile sdk`（JSON-RPC）驱动自研前端 | UI 完全自主、体积最小                          | 需重新实现会话/插件/设置全套 UI；SDK 接口在 developer preview 阶段不稳，追新版本维护重 | 暂不采用，远期备选         |
| D. 官方 apps/desktop     | 直接给官方 Electron 应用出包        | 官方架构完整                                     | 需要生产签名/公证/更新托管环境（DeepSeek 官方 COS 等），非官方团队不可复制 | 不采用                     |
| E. VS Code 扩展          | 在编辑器内集成 dsh                  | 贴近开发者                                       | 与"独立桌面 App、面向小白用户"的目标不符                   | 不采用                     |

> 方案 C 的存在价值：如果未来 dsh SDK 稳定且需要深度定制 UI（例如面向更轻量的场景），可以在保持壳不变的前提下替换渲染层，属于远期演进方向，不影响当前选型。

## 推荐方案：薄壳 Electron + 回环加载官方 Web UI

### 总体架构

```text
┌─────────────────────────────────────────────┐
│ Electron App（Otter Shell）                 │
│                                             │
│  ┌──────────────┐   ┌─────────────────────┐ │
│  │ Main 进程     │   │ Renderer            │ │
│  │  - 单实例锁   │   │  - 官方 dsh Web UI  │ │
│  │  - dsh 生命周期│   │   （loadURL 回环）  │ │
│  │  - 托盘/窗口  │   │  - Otter 附加条     │ │
│  │  - 更新检查   │   │    （版本/状态）    │ │
│  └──────────────┘   └─────────────────────┘ │
│         │ child_process                     │
│         ▼                                   │
│  Node.js（内置）─ dsh web --no-open         │
│         │                                   │
│         ▼                                   │
│  http://127.0.0.1:<随机端口>                │
└─────────────────────────────────────────────┘
```

**进程与通信模型**：

- Main 进程持有单实例锁（`app.requestSingleInstanceLock`），第二个实例只唤起已有窗口。
- Main 用 `child_process.spawn` 启动内置 Node.js 跑 `dsh web --no-open --port <p>`，随机端口避免冲突；轮询 `stdout`/`stderr` 识别启动完成信号，失败则重试（最多 3 次，指数退避）。
- `BrowserWindow` 通过 `loadURL` 加载官方 UI 的回环地址。**不做 custom protocol、不做 request handler 拦截**——保持薄壳定位，官方 UI 的静态资源和 WS/流式接口都直接走回环 HTTP。
- 关闭窗口不退出（驻留托盘），真正退出时先向子进程发 SIGTERM，超时后再 kill，并确认端口已释放。
- 沙箱配置：`sandbox: true` + `contextIsolation: true`，Renderer 不开 nodeIntegration。
- **自动更新**：electron-updater + GitHub Releases，`latest.yml` 由 electron-builder 自动生成，无需自建后端。

### dsh 版本策略（核心问题）

这是整个项目最大的分寸问题：**绑定太死会失去插件生态（插件装不上新 dsh），完全不绑会碎成无数未测组合**。官方 desktop 的选择是"Electron 壳与 dsh 精确同版本"，社区 dsh-desktop 的选择是"pin 上游 + 独立 workspace"，都是重方案。Otter 是个人/小团队项目，采用**松耦合策略**：

- Otter 安装包不内置 dsh 运行时依赖，首次启动时在线安装指定版本（`@deepseek-ai/dsh` 精确版本，记录在 `upstream.json`）。
- 首次启动流程：安装引导页（含安全须知摘要）→ 在线安装 dsh → 启动 Web UI。
- 每个 Otter 版本发布前人工/CI 验证对应 dsh 版本组合，但不阻止用户在设置里切换其他 dsh 版本（自担风险，UI 明确提示）。
- 上游 breaking change 应对：dsh 处于 developer preview，破坏性变更频发。Otter 每次发版前跑一遍"冒烟清单"（启动 → 新建会话 → 发一条消息 → 装一个示例插件 → 重启），组合不通过就升级 pin 的 dsh 版本。
- CLI 与桌面共享 `$DSH_HOME` 产品数据（会话/设置/凭据），但 Otter 用独立 profile（如 `$DSH_HOME/profiles/otter`）管理可执行包，避免与 CLI 互相污染——与官方 desktop 的做法一致，这是它文档里明确强调的隔离原则。

### 功能范围（v1）

| 功能               | 说明                                                        |
| ------------------ | ----------------------------------------------------------- |
| 一键安装、开箱即用 | NSIS 安装器 / macOS DMG，无需预装 Node.js（App 内置运行时） |
| 自动管理 dsh 后端  | 启动、健康检查、崩溃重启、退出清理                          |
| 窗口 + 系统托盘    | 关窗驻留托盘；托盘菜单：显示/隐藏、检查更新、退出           |
| 自动更新           | electron-updater + GitHub Releases                          |
| dsh 版本管理       | 默认 pin 精确版本，设置页可查看/切换                        |
| 日志与诊断         | 落盘日志（滚动）；"导出诊断包"（日志 + 版本信息，供 issue 上报） |
| 多语言             | 跟随系统，简中/英文                                         |

**v1 明确不做**：手机远程控制、多 profile 热切换、自研 UI、插件市场镜像、Linux 支持（官方 desktop 也不支持 Linux）。

### 打包与发布

- **工具链**：pnpm workspace + electron-vite + electron-builder。
- **体积与更新**：安装包约 150–200 MB（Electron ~100 MB + 内置 Node 运行时 + dsh 依赖）。自动更新走 GitHub Releases（electron-updater generic provider），差分包（blockmap）可显著降低升级流量。
- **平台矩阵**：v1 只做 Windows x64 + macOS Universal（苹果双架构），与官方 desktop、社区 dsh-desktop 的支持面一致。
- **发版流程**：更新 `upstream.json`（dsh 版本）→ 出包（`package:win:x64` / `package:mac`）→ 冒烟清单 → tag + GitHub Release（安装包 + `latest.yml`）。
- **签名**：v1 不签名（个人项目无证书预算）。Windows SmartScreen 告警与 macOS Gatekeeper"右键打开"引导写入 FAQ；远期用户量起来后再评估代码签名证书。

### 风险与缓解

| 风险                                 | 缓解                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------- |
| dsh developer preview 频繁破坏性变更 | 松耦合 pin + 冒烟清单 + Otter 不改上游一行代码                                           |
| dsh 升级后历史会话格式不兼容         | 会话数据在上游 `$DSH_HOME`，与 Otter 无关；Otter 只管理自己的 profile，升级前提示备份    |
| 回环端口被占用                       | 随机端口 + 启动重试；诊断包里记录端口与启动日志                                          |
| Electron 体积大                      | 已评估 Tauri（见对比表），因需捆绑 Node 运行时体积优势蒸发，接受 Electron                 |
| 社区 dsh-desktop 已占先发            | 差异化定位：Otter 面向最简使用路径（首次启动安装引导、诊断导出、文档中文化等"包装"价值） |
| 官方 apps/desktop 成熟后接管市场     | Otter 的核心价值是学习与可定制；若官方 desktop 满足需求，用户自然迁移，Otter 保持小而清晰的参考实现定位 |

## 立即可做的第一步

1. 建立 pnpm workspace 骨架（electron-vite + electron-builder）。
2. Main 进程实现"spawn 内置 Node → `dsh web --no-open` → 随机端口 → loadURL"最小闭环。
3. 先用 `:dir` 目标（免安装目录版）跑通冒烟清单，再接 NSIS/DMG 打包。

后续每完成一个阶段（最小闭环、托盘/更新、签名发布），在本文件追加更新记录并在 `docs/` 下补充模块文档。
