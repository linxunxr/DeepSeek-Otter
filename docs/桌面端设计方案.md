# DeepSeek-Otter 桌面端设计方案

把 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（下称 dsh）打包成 Windows / macOS 桌面应用的产品与技术设计。设计目标按优先级排序：**资源占用低 > 启动快 > 功能全**。README 面向人，介绍项目定位与方案结论；实现细节随代码演进放在各模块文档中。

## 项目定位

dsh 是 DeepSeek 官方的开源 agent harness，一切皆插件（基于 Cordis 框架），默认形态是 `npx @deepseek-ai/dsh web` 启动本地 Web UI（`http://127.0.0.1:3080`）。它要求用户先装 Node.js、会用命令行，普通用户无法直接使用。

DeepSeek-Otter（水獭）的目标：**让不懂命令行的用户也能一键安装、开箱即用地用上 dsh**——下载即用，无需 Node.js、无需终端，自动管理 dsh 后端与版本，并以桌面 App 的形态提供窗口、托盘、更新等原生体验；同时保持轻量：不用时几乎不占内存，用时资源开销贴近"一个浏览器标签页 + 一个 Node 进程"的下限。

一句话：**Otter 是 dsh 的轻量桌面发行版（desktop distribution），对上游只做"打包与包装"，不 fork 功能。**

## 调研结论（选型的依据）

截至 2026-09 的三个关键事实：

1. **官方仓库已内置 Electron 桌面应用**（`apps/desktop`）。它的设计非常重：Electron 与 `@deepseek-ai/dsh` 绑定精确版本、内置离线 pnpm 种子、私有 `dsh-app://` 协议承载 Fetch 流量（不开任何监听端口）、staging/健康检查/回滚的激活事务。它解决的是"官方签名发行"问题，需要 macOS 公证、Windows EV 证书等生产发布环境，门槛高（相关文档：`docs/architecture.md` 的 "Desktop application" 一节、`apps/desktop/README.md`）。
2. `dsh web` 就是一个**完整的 Web UI**（会话、插件市场、设置、凭据都在里面），并且 dsh 提供多种启动 profile：`web`（Web 服务）、`headless`（一次性运行）、`sdk` / `sdk-minimal`（JSON-RPC SDK 服务）、`acp`（自动化协议服务）。这是桌面壳可以复用的核心资产。
3. **社区已有同类先例**：anywhere-labs/dsh-desktop（约 2.5 万 star），采用"薄 Electron 宿主 + 回环 HTTP/WS 加载官方 Web UI"路线，验证了这条路是通的且社区认可。

**推论：不要自研 Web UI，也不要 fork dsh**。官方 Web UI 就是产品本体，桌面壳只负责进程管理、窗口和原生集成。自研 UI 面对的是 developer preview 阶段"每周都在变的 API"（官方明示会有破坏性变更），维护成本不可控；而 Web UI 由上游随版本一起发布，天然同步。

**壳框架的选择则是开放问题**，由下一节的资源预算决定：渲染的都是同一个 dsh Web UI，差别只在壳进程本身（Electron 整个 Chromium+Node 壳 vs Tauri 的 Rust 壳 + 系统 WebView）。

## 资源占用预算（选型的硬约束）

以下为典型量级估算（Windows x64，空闲态，实际随会话数与插件数浮动），用于方案对比，非承诺值。渲染同一份 dsh Web UI 时，浏览器引擎部分（Chromium / WebView2）开销相近，**真正的差别在壳进程与磁盘**：

| 组件                 | Electron 方案         | Tauri 2 方案              |
| -------------------- | --------------------- | ------------------------- |
| 壳进程               | 80–120 MB（Chromium+Node 主进程） | 10–20 MB（Rust）          |
| 渲染 dsh Web UI      | 250–400 MB（自带 Chromium） | 250–400 MB（系统 WebView2 / WKWebView，系统级共享） |
| dsh 后端（Node 子进程） | 150–250 MB          | 150–250 MB（相同）        |
| **活跃态合计**       | **~480–770 MB**       | **~410–670 MB**           |
| **关窗驻留态（后端已停）** | **~100 MB（仅剩 main 进程）** | **~15 MB（仅剩 Rust 壳）** |
| 安装包体积（不含 dsh） | ~120–150 MB          | ~35–45 MB（含 Node sidecar 压缩包） |
| 解压后磁盘           | ~250–350 MB           | ~110–130 MB（Rust 壳 ~20 MB + node.exe ~80 MB + 前端资源） |
| 壳升级流量           | 100 MB+（blockmap 差分后仍数十 MB） | ~35 MB 全量（小到不需要差分） |

结论：**性能优先的约束下 Tauri 2 胜出**——驻留态内存约为 Electron 的 1/7，磁盘约为 1/3，且 WebView2（Windows）与 WKWebView（macOS）由系统维护、多应用共享运行时。Electron 的开发效率优势不足以抵消这份常驻开销。

另有一个比壳框架更大的杠杆：**dsh 后端进程的生命周期**（见"后端生命周期策略"一节）——后端空闲时仍占 150–250 MB，"不用即停"比换框架省得更多。

## 候选方案对比

| 方案                      | 思路                                  | 优点                                               | 缺点                                                                 | 结论                 |
| ------------------------- | ------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------- | -------------------- |
| A. Tauri 2 薄壳 + Web UI  | Rust 壳起 `dsh web`，系统 WebView 加载回环地址 | 壳进程 ~15 MB、磁盘小、更新流量小；WebView 系统级共享；托盘/单实例/更新均有官方插件 | 需 Rust 工具链（壳面积小，可控）；macOS WKWebView 与 Chromium 有兼容差异需验证 | **推荐（性能优先）** |
| B. Electron 薄壳 + Web UI | Electron 起 `dsh web`，窗口加载回环地址 | 生态成熟、纯 TS 开发效率最高；社区 dsh-desktop 已验证 | 壳进程 100 MB 级、磁盘 250 MB+，与"占用低"目标冲突                   | 备选（不接受 Rust 时） |
| C. 自研 UI + SDK profile  | `dsh --profile sdk`（JSON-RPC）驱动自研原生/轻量前端 | 无浏览器引擎，内存最优                             | 需重新实现会话/插件/设置全套 UI；SDK 接口在 developer preview 阶段不稳 | 暂不采用，远期备选   |
| D. 官方 apps/desktop      | 直接给官方 Electron 应用出包          | 官方架构完整                                       | 需要生产签名/公证/更新托管环境（DeepSeek 官方 COS 等），非官方团队不可复制；Electron 重壳与性能目标冲突 | 不采用               |
| E. VS Code 扩展           | 在编辑器内集成 dsh                     | 贴近开发者                                         | 与"独立桌面 App、面向小白用户"的目标不符                             | 不采用               |

> 方案 C 的存在价值：如果未来 dsh SDK 稳定且需要极限低占用（无浏览器引擎），可以在保持壳不变的前提下替换渲染层，属于远期演进方向，不影响当前选型。

## 推荐方案：Tauri 2 薄壳 + 回环加载官方 Web UI

### 总体架构

```text
┌───────────────────────────────────────────────┐
│ Tauri App（Otter Shell，Rust）                │
│                                               │
│  ┌──────────────────┐  ┌───────────────────┐  │
│  │ 壳进程（Rust）    │  │ WebView（系统）    │  │
│  │  - 单实例         │  │  - 官方 dsh Web UI│  │
│  │  - 后端生命周期   │  │  - Otter 引导/设置│  │
│  │  - 托盘/更新      │  │    /诊断页（本地）│  │
│  └──────────────────┘  └───────────────────┘  │
│         │ spawn                               │
│         ▼                                     │
│  node.exe（内置 sidecar）─ dsh web --no-open  │
│         │                                     │
│         ▼                                     │
│  http://127.0.0.1:<随机端口>                  │
└───────────────────────────────────────────────┘
```

**进程与通信模型**：

- 壳进程通过 `tauri-plugin-single-instance` 保证单实例，第二个实例只唤起已有窗口。
- Rust 侧 `spawn` 内置 node.exe sidecar 跑 `dsh web --no-open --port <p>`，随机端口避免冲突；解析 `stdout`/`stderr` 识别启动完成信号，失败重试（最多 3 次，指数退避）。
- WebView 加载官方 UI 的回环地址。**不做 custom protocol、不做请求拦截**——保持薄壳定位，官方 UI 的静态资源和 WS/流式接口都直接走回环 HTTP。
- 引导/设置/诊断页是壳自带的本地静态页（后端尚未就绪时也要能显示），与 dsh Web UI 分离。
- 沙箱：WebView 默认无 Node 访问；远程内容（回环 dsh）不授予任何 Tauri IPC 权限（capability 只绑定本地页面）。
- **自动更新**：`tauri-plugin-updater` + GitHub Releases，壳体积小（~35 MB），全量更新即可，无需差分。

### 后端生命周期策略（降占用的最大杠杆）

dsh 后端空闲时也要 150–250 MB，是常驻内存的最大单项。Otter 的原则是**"不用即停、用时速启"**：

| 状态           | 后端进程     | 说明                                                       |
| -------------- | ------------ | ---------------------------------------------------------- |
| 活跃（窗口开） | 运行         | 正常使用                                                   |
| 关窗驻留托盘   | **停止**     | 默认行为。点开托盘时重启后端并恢复窗口（目标 < 5 s）       |
| 后台任务运行中 | 运行         | dsh 存在 `ctx.jobs` 后台任务；关窗前若检测到活跃会话/任务，提示用户选择"停止"或"继续跑完"，也可在设置中固定为"驻留直到任务结束" |
| 退出应用       | 停止         | 先 SIGTERM，超时后 kill，确认端口释放                      |

- 退出与停止的清理路径一致：SIGTERM → 超时 kill → 端口释放确认。
- 崩溃自动重启：后端异常退出且窗口开着时，重试 3 次；连续失败则展示诊断页（日志 + 重试按钮）。
- 首次启动（含在线安装 dsh）单独走引导页，不适用 < 5 s 目标。

### dsh 版本策略（核心问题）

这是整个项目最大的分寸问题：**绑定太死会失去插件生态（插件装不上新 dsh），完全不绑会碎成无数未测组合**。官方 desktop 的选择是"Electron 壳与 dsh 精确同版本"，社区 dsh-desktop 的选择是"pin 上游 + 独立 workspace"，都是重方案。Otter 是个人/小团队项目，采用**松耦合策略**：

- Otter 安装包不内置 dsh 运行时依赖，首次启动时在线安装指定版本（`@deepseek-ai/dsh` 精确版本，记录在 `upstream.json`）。
- 首次启动流程：安装引导页（含安全须知摘要）→ 在线安装 dsh → 启动 Web UI。
- 每个 Otter 版本发布前人工/CI 验证对应 dsh 版本组合，但不阻止用户在设置里切换其他 dsh 版本（自担风险，UI 明确提示）。
- 上游 breaking change 应对：dsh 处于 developer preview，破坏性变更频发。Otter 每次发版前跑一遍"冒烟清单"（启动 → 新建会话 → 发一条消息 → 装一个示例插件 → 关窗再开），组合不通过就升级 pin 的 dsh 版本。
- CLI 与桌面共享 `$DSH_HOME` 产品数据（会话/设置/凭据），但 Otter 用独立 profile（如 `$DSH_HOME/profiles/otter`）管理可执行包，避免与 CLI 互相污染——与官方 desktop 的做法一致，这是它文档里明确强调的隔离原则。

### 打包与发布

- **工具链**：pnpm workspace + Vite（壳本地页面）+ Tauri 2 CLI（bundler 集成 NSIS / DMG）。
- **sidecar**：node.exe 作为 Tauri externalBin 打包（Windows x64 官方 Node.js 二进制，SHA-256 校验后注入）；dsh 本体首次启动在线安装，不进安装包。
- **平台矩阵**：v1 只做 Windows x64（WebView2 为 Chromium 内核，与 dsh Web UI 的开发测试环境一致，兼容风险低）；macOS Universal 在 WebKit 兼容性验证通过后跟进（见风险表）。
- **发版流程**：更新 `upstream.json`（dsh 版本）→ `pnpm tauri build` 出包 → 冒烟清单 → tag + GitHub Release（安装包 + updater 元数据，minisign 签名）。
- **签名**：v1 不签名（个人项目无证书预算）。Windows SmartScreen 告警与 macOS Gatekeeper"右键打开"引导写入 FAQ；远期用户量起来后再评估代码签名证书。

### 风险与缓解

| 风险                                 | 缓解                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| dsh developer preview 频繁破坏性变更 | 松耦合 pin + 冒烟清单 + Otter 不改上游一行代码                                                   |
| dsh 升级后历史会话格式不兼容         | 会话数据在上游 `$DSH_HOME`，与 Otter 无关；Otter 只管理自己的 profile，升级前提示备份            |
| macOS WKWebView（WebKit）与 Chromium 渲染/行为差异 | v1 先只发 Windows（WebView2 同为 Chromium 内核）；macOS 出包前先跑完整冒烟，不通过则标记 beta |
| Rust 工具链门槛                      | 壳面积刻意最小化：spawn/托盘/单实例/更新全用官方插件与 API，Rust 侧只写生命周期状态机            |
| Windows 老机器缺 WebView2            | Tauri 打包 WebView2 bootstrapper，安装器自动补装（Win11 自带）                                   |
| 回环端口被占用                       | 随机端口 + 启动重试；诊断包里记录端口与启动日志                                                  |
| 关窗即停导致后台任务中断             | 关窗前检测活跃会话/任务并提示；设置页提供"驻留直到任务结束"选项                                  |
| 社区 dsh-desktop 已占先发            | 差异化定位：Otter 面向最简使用路径 + 低占用（关窗 ~15 MB 驻留），不与它拼功能全                  |
| 官方 apps/desktop 成熟后接管市场     | Otter 的核心价值是轻量与可定制；若官方 desktop 满足需求，用户自然迁移，Otter 保持小而清晰的参考实现定位 |

## 立即可做的第一步

1. 搭 Tauri 2 工程骨架（Vite + Tauri CLI），配置 node.exe sidecar 与 WebView2 bootstrapper。
2. Rust 侧实现"spawn node sidecar → `dsh web --no-open` → 随机端口 → WebView loadURL"最小闭环（开发期 dsh 可先手动预装，在线安装引导随后补）。
3. 实现生命周期状态机第一版：关窗 → 停后端驻留托盘；点开 → 重启后端恢复窗口。
4. 先用免安装目录版跑通冒烟清单（含关窗/再开），再接 NSIS 打包。

## 实现记录（2026-09-09，最小闭环）

第一~三步已完成并实测通过，关键落地细节（部分与设计稿有出入，以本节为准）：

- **就绪信号与 URL 解析**：实测 dsh web 打印 `dsh web: http://127.0.0.1:<port>/?token=<…>`；URL 带 token 才可访问（不带返回 401），因此壳不自拼 URL，从 stdout 解析就绪行（前缀 `dsh web:`）。启动命令用 `--port 0` 让 OS 分配端口（dsh 原生支持），省去自选端口的竞态。
- **Windows 启动链**：release 子系统（windows_subsystem="windows"）下 `Command::new("npx")` 会失败——npx 实为 `npx.cmd`。统一走 `cmd /C npx -y @deepseek-ai/dsh web --no-open --port 0`；实际进程链为 cmd → npx-cli(node) → cmd → dsh(node)。
- **进程树终止**：`taskkill /PID <pid> /T /F` 一次调用可终止整条链并释放监听端口（实测验证），无需 SIGTERM 分级。
- **壳页面 URL**：dev 模式是 devUrl（http://localhost:1420），打包后是 `http://tauri.localhost`，不可硬编码；启动时记录窗口初始 URL，"回壳页面"导航复用。
- **实测内存**：壳进程 66.5 MB（含 WebView2 宿主），WebView2 全家 1.5 GB 工作集含共享 GPU/存储进程，与其他 WebView2 应用共享；dsh 后端 node 进程单独 ~150 MB。驻留态（关窗停后端）待实测。

### 自管运行时（2026-09-10 落地）

目标：目标机器**无需安装 Node.js、不依赖系统 PATH**。三层结构：

| 层      | 打包方式                        | 运行时位置                                                    |
| ------- | ------------------------------- | ------------------------------------------------------------- |
| node    | Tauri externalBin（v24.21.0）   | exe 同级 `node.exe`（NSIS 安装根目录）                        |
| npm CLI | resources（`runtime/npm.tgz`）  | 首次解包到 `<appData>/dsh-runtime/npm/package/`               |
